# TEE FTL V2 prototype

V2 contains the complete V1 visible-range and protected/pending write guards,
then adds active/passive chunk metadata, HMAC-SHA256 groups, persisted-style
state caching, protected write classification, and passive relocation checks.

## Geometry and wire format

- The logical segment size is configurable and defaults to 512 bytes.
- FEMU page size is obtained from `secs_per_pg * secsz` during policy init.
- `segments_per_page` is computed as `page_size / segment_size`; no LPC 2048-byte
  page assumption is used.
- Protected and pending bitmaps contain one bit per logical segment.
- Segment headers are parsed bytewise: magic `0xA7`, one-byte file ID, three-byte
  little-endian chunk ID, and one-based little-endian 32-bit segment index.
- HMAC-SHA256 covers complete logical segments, including their headers, in
  ascending segment-index order. The prototype uses a fixed 32-byte key.
- HMAC group count is metadata-driven and independent of FEMU page geometry.
  The default pending group capacity is 64.

## State ownership

- Active metadata, arrived/pending state, pending bitmap, HMAC working state,
  and relocation trace are RAM working state and are not cache entries.
- The V2 cache exposes only persisted-style protected bitmap and passive chunk
  metadata access. Durable hidden-region storage and cache writeback are later
  version work.
- Metadata intake is available through `tee_v2_policy_set_active_metadata()` as
  an internal/test API. NVMe admin command intake is intentionally not in V2.

## Write and relocation flow

The policy preflights the complete request without mutating metadata. Protected
or pending destinations, duplicate active indexes, and changed passive data are
rejected before the media write. Policy state is published only after all input
bytes are consumed and every touched FEMU page reports a successful backend
program status. Active arrivals are then recorded, complete HMAC groups are
verified or reused, failed groups have
their pending bits cleared, and a fully arrived/verified chunk is promoted to
passive state and marked protected.

Passive relocation compares every incoming segment byte with the old mapped SSD
segment. Identical data is accepted. V2 records and applies the required order:
mark the new logical location before removing the old mark. Durable relocation
transactions and rollback are deferred to V4.

DSM ranges use the same protected/pending range guard as writes. Replacing or
clearing active metadata releases only its RAM pending bits and does not change
passive metadata or protected bits.

## Deferred work

- V3: protected-read metadata flow, hidden metadata storage, and pending timeout.
- V4: authenticated admin commands, pagination, durable cache writeback, and
  chunk/relocation transactions.
- V5: complete policy status behavior, delete, rollback reporting, and proof
  error details.
