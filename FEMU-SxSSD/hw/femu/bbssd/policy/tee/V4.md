# TEE FTL V4 implementation status

Restore point: `feabc94c49e866de694d1f6f7251b73844b52a12`

V4 retains the V1 segment/bitmap/guard path, the V2 metadata, write, cache,
and relocation path, and the V3 protected metadata/read/proof path. It adds
the custom NVMe admin-command boundary through which authenticated metadata is
installed and protected state is queried.

Implementation status: complete for the current software-test prototype. The
continuous policy test exercises the V1-V3 behavior through the V4 admin
boundary and inherited policy operations. The normal NVMe WRITE callback's
real media fixture was not available, and real FEMU execution remains
user-gated.

## Authenticated admin protocol

- Vendor admin opcodes are `SUBMIT`, `FETCH`, and `CONTINUE`.
- Every operation carries the fixed V4 request header and a 32-byte request
  MAC. HMAC-SHA256 covers the fixed header bytes before `request_mac`, followed
  by exactly the declared payload bytes.
- The mutually exclusive `SUBMIT`, `FETCH`, and `CONTINUE` flags are included
  in the authenticated header. They domain-separate the operations: a valid
  signed SUBMIT cannot be reused as a FETCH or CONTINUE authorization.
- The parser requires the exact operation flag, exact request length, declared
  payload length, command-specific payload shape, zero reserved bytes where
  specified, and a valid MAC before dispatch.
- Successful SUBMIT request IDs must increase monotonically. A duplicate or
  older SUBMIT is rejected without replacing the pending response. FETCH and
  CONTINUE must authenticate and match the pending command and request ID;
  CONTINUE also binds its payload request ID and page index.
- The current prototype uses the V2 prototype key. Production key provisioning,
  a derived administrator key, and response MACs are deferred to V6.

Files: `tee/tee-v4-admin-format.[ch]`, `tee/tee-v4-admin.[ch]`.

## Metadata intake and V1-V3 compatibility

- `SET_ACTIVE_METADATA` is the authenticated V4 admin intake command. It
  replaces the V2 test-only metadata-injection path at the V4 policy boundary.
- The command validates the fixed metadata payload, exact HMAC-group array
  size, group coverage, segment count, coding coefficient, chunk range, and
  reserved fields before changing state.
- The V4 policy converts the wire HMAC groups into V2 group specifications and
  installs a new V2 active-metadata/write context atomically. A failed parse or
  intake callback leaves the prior state and pending response intact.
- Normal data processing remains on the inherited V1-V3 policy path. V2 write
  completion promotes passive metadata into the V3 hidden metadata store, and
  V4 records the associated chunk-commit transaction.
- V2's direct constructors and injection helpers remain available for V1-V3
  unit tests. They are test/setup APIs, not the V4 NVMe metadata-ingress path.

Files: `tee-ftl-v4-policy.[ch]`, `tee/tee-v2-write.[ch]`,
`tee/tee-v3-policy.[ch]`.

## Paginated protected reads

- Authenticated SUBMIT supports `READ_SUMMARY`, `READ_LOCATIONS`,
  `READ_HMAC_GROUPS`, and `ONE_BIT_PROOF`.
- The requested `page_size` controls items per page, bounded by what fits after
  the response header in the configured admin buffer. Zero selects the maximum
  that fits. Summary and a non-missing one-bit proof are single-item results.
- FETCH returns page zero. CONTINUE returns the authenticated requested later
  page. Response headers report total items, item size, total pages, page index,
  start item, and returned items.
- Each policy instance owns exactly one pending response. A successful newer
  SUBMIT replaces it; rejected requests leave it unchanged.

Files: `tee/tee-v4-admin-response.[ch]`, `tee/tee-v4-admin.[ch]`.

## Writeback transactions and SYNC

- V4 installs hooks into the inherited V2 write path. Completed chunk promotion
  emits an immediate chunk-commit transaction.
- Relocations reserve V4 transaction records before the inherited move is
  accepted. Records contain transaction ID, file/chunk, segment index, old and
  new locations, and transaction state.
- Relocation records flush at capacity, after the configured operation timeout,
  or on authenticated `SYNC_METADATA`. Failed flushes retain pending records so
  they can be retried.
- If a later part of the normal write callback fails after relocation
  reservations were made, the callback cancels those reservations. Operation
  advancement propagates timeout-flush failure instead of silently losing it.
- The policy's current hidden backend stores the V3 metadata image and persisted
  transaction sink in process memory. Transaction replay and the hidden backend
  are therefore not durable across process restart or reboot.

Files: `tee/tee-v4-writeback.[ch]`, `tee-ftl-v4-policy.c`,
`tee-ftl-v1-policy.c`, `tee/tee-v2-write.[ch]`.

## Software verification

The V4 Makefile target includes:

- `test_tee_v4_admin_format`: fixed layout, MAC span, and operation flags.
- `test_tee_v4_admin_response`: response paging and bounds.
- `test_tee_v4_writeback`: commit, batching, timeout, failed-flush retention,
  retry, reservation cancellation, and sync.
- `test_tee_v4_admin`: signed SUBMIT/FETCH/CONTINUE, strict size checks,
  operation-domain separation, pending-response lifecycle, page-size behavior,
  replay rejection, and SYNC failure/retry.
- `test_tee_v4_metadata_intake`: valid `SET_ACTIVE_METADATA`, strict malformed
  payload rejection, and intake failure atomicity.
- `test_tee_v4_policy_flow`: one continuous software flow through the actual V4
  NVMe admin callback for metadata intake and paginated reads, plus the exact
  inherited post-media write operation that performs V2 completion, V3
  persistence, and V4 chunk-commit writeback.

The V1, V2, and V3 test suites remain compatibility coverage and may use their
direct setup helpers. The V4 flow test is the coverage that proves those layers
operate beneath the V4 command boundary.

## Explicit validation boundaries

- The continuous software flow does not invoke the inherited normal NVMe WRITE
  callback against a real block-media fixture; it invokes that callback's exact
  post-media policy operation because the fixture is unavailable.
- No real FEMU emulator run has been performed. Starting real FEMU is a
  user-approval gate.
- The hidden backend and persisted transaction records are process-memory
  prototypes. Reboot-durable storage, recovery, and transaction replay are not
  implemented.
- Production administrator keys, key derivation/provisioning, and response MACs
  are deferred to V6.

These boundaries do not block building V5 on the software V4 implementation,
but they must not be represented as real-target or crash-recovery validation.
