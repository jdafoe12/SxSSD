# TEE FTL V5 implementation status

Restore point: V4 commit `601a9b23883f1a0214ffbeec0128f9fef5bf7537`.

V5 retains the V1 segment parsing and write guards, V2 active/passive metadata
and HMAC write flow, V3 hidden metadata/read/proof behavior, and V4 authenticated
NVMe admin transport and writeback transactions. It adds explicit policy status
responses, chunk-scoped `DELETE` and `ABORT_ACTIVE`, transactional deletion,
and identity-scoped proof errors.

Implementation status: complete for the current software-test prototype. This
status does not mean that the policy has run in a real FEMU process or on LPC
hardware; those validations remain separately gated.

## Actual metadata and command path

V5 uses V4's vendor NVMe admin opcodes for `SUBMIT`, `FETCH`, and `CONTINUE`.
Requests use the fixed V4 header and its 32-byte request MAC. HMAC-SHA256 covers
the fixed header bytes before `request_mac`, followed by exactly the declared
payload. V4's strict operation flags, length checks, replay rules, pagination,
and one-pending-response-per-policy rule remain in force.

`SET_ACTIVE_METADATA` is handled through that authenticated admin path. The V5
policy installs the validated metadata into the inherited V2 active write
context; it does not use V2's internal/test-only metadata injection as its
external intake path. The direct V1-V3 helpers remain available only for their
unit and compatibility tests.

The inherited authenticated commands remain available:

- `SET_ACTIVE_METADATA`
- `READ_SUMMARY`
- `READ_LOCATIONS`
- `READ_HMAC_GROUPS`
- `ONE_BIT_PROOF`
- `SYNC_METADATA`

V5 adds command type `7` (`DELETE`) and command type `8` (`ABORT_ACTIVE`). Both
use an exact packed eight-byte identity payload:

```text
u8  file_id
u8  reserved[3]     // all zero
u32 chunk_id        // 0x000000 through 0xFFFFFF
```

The request header, operation, identity payload, reserved bytes, length, and
MAC are validated before a handler is called. A rejected request does not
replace the existing pending response.

## ABORT_ACTIVE

`ABORT_ACTIVE` is exact-identity and idempotent. If `(file_id, chunk_id)` is the
current active chunk, V5 destroys that active metadata and HMAC working state,
clears its RAM pending bitmap, and clears only that identity's stored proof
error. An absent or nonmatching identity still returns `OK`, but does not alter
the active chunk, passive metadata, protected bitmap, or another chunk's proof
error.

`DELETE` never implicitly aborts active state. A caller must submit
`ABORT_ACTIVE` first when the same identity is active.

## DELETE

Deletion is scoped to exactly `(file_id, chunk_id)`. It removes the passive
metadata record and rebuilds the protected bitmap from the remaining passive
records. It does **not** erase or overwrite physical media data.

Before deletion, V5 flushes inherited V4 writeback transactions. It then checks
the passive-record structure, complete verified HMAC-group coverage, location
bounds, and consistency between recorded locations and protected bits. This is
a metadata/bitmap integrity check; V5 does not reread media and recompute the
chunk HMAC during deletion.

The deletion is prospective and persist-first: V5 constructs a complete
candidate cache image, persists that image through the V3 hidden-storage
backend, and publishes it to RAM only after persistence succeeds. A persistence
failure leaves the prior RAM cache in place. Deleting an absent passive chunk
returns `NOT_FOUND` without changing state. Deleting the currently active
matching chunk returns `BAD_REQUEST` and records a delete-conflict proof error.

## Status behavior

The V5 response status values are stable:

| Value | Status |
|---:|---|
| 0 | `OK` |
| 1 | `NOT_FOUND` |
| 2 | `BAD_REQUEST` |
| 3 | `NO_PENDING_RESPONSE` |
| 4 | `INTERNAL_ERROR` |
| 5 | `BAD_MAC` |
| 6 | `MALFORMED` |
| 7 | `UNSUPPORTED` |

Policy-level results, including `NOT_FOUND`, `BAD_REQUEST`, malformed or
unsupported authenticated requests, are carried in the fetched response and
map to NVMe success. `INTERNAL_ERROR` maps to `NVME_INTERNAL_DEV_ERROR` without
the DNR bit so a caller may retry. Transport/framing failures can still reject
the NVMe command directly.

## Proof error behavior

V5 proof errors are scoped to `(file_id, chunk_id)`. An error recorded for one
chunk takes precedence only when `ONE_BIT_PROOF` queries that same identity; it
does not shadow or replace evidence for another active or passive chunk. The
prototype retains up to eight independent identity errors. If that table is
full, recording a ninth identity fails closed without evicting existing
evidence. The originating operation retains its normal command status; for
example, active-delete conflict remains `BAD_REQUEST`, while persistence and
integrity failures remain internal failures. Updating an existing identity does
not consume another slot. A successful matching
`SET_ACTIVE_METADATA`, matching `ABORT_ACTIVE`, or successful matching `DELETE`
clears only the corresponding entry. An unrelated or absent abort does not.

The inherited V3 error API remains a single legacy, unscoped error for V3/V4
compatibility. Recording through that API explicitly replaces scoped V5 error
state; it never inherits a stale V5 identity. V5 operations use the scoped API.

Error codes are:

| Value | Error |
|---:|---|
| 0 | `NONE` |
| 1 | `HMAC_FAILURE` |
| 2 | `PERSISTENCE_FAILURE` |
| 3 | `DELETE_INTEGRITY` |
| 4 | `DELETE_CONFLICT` |
| 5 | `INTERNAL` |

`failed_segment_index` is one-based when a particular segment is responsible.
`UINT32_MAX` means that the failure is not attributable to one segment.

## V1-V4 compatibility

The V5 shared policy is layered over the actual V4 policy state and callbacks.
Normal NVMe data writes and DSM requests still enter the inherited V1/V2 path;
completed chunks still promote into V3 passive hidden metadata; V4 transaction
writeback still records chunk commits and relocation changes. V4 admin reads,
pagination, continuation, metadata intake, and sync are dispatched by the V5
admin wrapper unchanged.

The V1, V2, V3, and V4 focused and flow suites remain compatibility coverage.
Their direct setup helpers are retained so old-version tests describe those
versions accurately. The V4 and V5 continuous policy tests are the coverage for
the authenticated NVMe admin boundary rather than a rewritten claim that V1-V3
originally exposed that boundary.

That direct-GCC verification passed:

- V1 flow smoke test.
- V2 flow smoke test.
- V3 flow smoke test.
- V4 continuous policy flow.
- V5 status, admin format, admin dispatch, proof error, deletion, and continuous
  policy-flow tests.

In the compatibility run, all 25 already-built V1-V5 executables passed. After
the final proof-isolation fix, the proof test and V5 policy-flow test were
rebuilt with `-Werror` and passed, and the V5 shared policy was rebuilt
successfully. These direct builds and executions are the authoritative software
result for this environment.

The V5 continuous test enters through the actual V5 `SUBMIT`/`FETCH` callbacks
for authenticated metadata, abort, delete, proof, and status behavior. Like the
V4 continuous test, it invokes the inherited post-media policy operation for
write completion because a real block-media callback fixture is not available.

## Validation boundaries and lifecycle risk

- No real FEMU emulator run has been performed. Starting real FEMU remains a
  user-approval gate after commit/push.
- No LPC/IAR build, flash, debugger, board, or hardware validation has been
  performed.
- The hidden metadata backend and transaction sink remain process-memory
  prototypes; reboot recovery and replay are not implemented.
- V5 unregisters newly registered admin hooks when a later V5 hook registration
  fails. The inherited V4/V1 initialization path still lacks a complete
  teardown/unload API for all previously allocated state and registered hooks.
  Failed repeated initialization or dynamic unload/reload is therefore an
  acknowledged lifecycle risk and is not claimed as validated.

## Deferred to V6

- Production administrator-key provisioning and key derivation.
- Authentication of response data (response MACs).
- Reboot-durable hidden storage, recovery, and transaction replay.
- Resolution of the inherited complete initialization rollback/unload lifecycle.

These boundaries must be resolved or explicitly accepted before representing
V5 as crash-recoverable or production-ready, but they do not change the tested
V5 command and policy semantics described above.
